# 成品库优先：可单独安装的一项

## 目标与边界

先查持久库，唯一匹配直接发送已有成品，不联网取歌、不分离、不再次 RVC。没做过才进入原流程；同名不同版本或请求不同版本先澄清。失败发送不等于需要重做。原 Aurabot 1.1.11 是先搜索/下载再查有限缓存，不能代替这项能力。

随包 `assets/song-library/` 五份源文件是本技能提供的独立用户扩展，不是官方插件自带保证。依据 Aurabot 1.1.11 API 1 编写，只支持**主人私聊**、现有全局/翻唱开关与试运行模式。支持 `/sing` 及部分常见中文点歌句，并在同一个 `song.request` 对象方法上增加成品保护，使模型工具、面板和命令共用的请求先查库。支持 [清唱与上一首接续](acappella.md)，不能承诺任意聊天措辞、群聊、非主人、变音色/变调和多个模型组合均可直接复用。

历史实测故障：只拦 `message` 不够。“我要听……”未列为意图、“我说的是……”修正句未接管时，模型会调用 `qq_song_cover` 绕开消息监听。因此必须同时检查共用制作入口，不能只增加几句提示词。该方法包装是针对当前版本的兼容适配，不是宿主提供的稳定拦截 API；升级后核对对象引用、同步返回值、生命周期清理及新的制作入口。

**权限与现有行为先查**：扩展接管 `/sing` 时限制主人私聊；如果用户原来需要群聊或非主人点歌，原样安装会缩小既有功能。不能静默安装并宣称“完全保留”：先说明，按实际上游权限适配并补测试，或不安装此模板、保留原行为。不要为让成品发送而顺手打开真实外发、全局开关或正在关闭的翻唱功能。

只有歌曲库需求时，不要求重新安装 RVC/分离环境。若原生模块为缺环境而禁用，先检查开关与队列副作用；不能盲目启用后让未命中请求排队。用户只想重发、不想新制作时，应将未命中分支适配为提示“库中没有”，而不是调用 `api.use('song').request`。

## Agent 安装/更新

与[本机翻唱插件](breeze-cover.md)一起更新时，本包版本读取独立RVC清唱默认值，用户明确指定版本优先，仅主人私聊原生制作入口继承；明确写出Breeze的消息不被旧RVC缓存监听抢答。没有选择此适配就保持原行为，不为翻唱面板自动缩小群聊权限。安装器也支持 `--module song-library`，默认只检查且不写索引/配置。

1. 从所选宿主的 `/modules` 和实际配置定位用户模块根、`workspaceDir`、版本及 `safeMode`，按字段读取，不打印全部响应。检查 `api.on('message'/'send')`、`api.command`、`api.sendVoiceFile`、`api.use('song').request` 的签名与拦截优先级，及 `onDispose`、`every`、`context`；核实模拟器的发送捕获边界。源码确认模型工具、路由持有的 song 对象与 `api.use('song')` 返回同一个对象；不是同一对象则当前保护无效，先适配。已有其他扩展包装 request 时先检查兼容性，不抢占。不同版本先适配，不强制关闭安全模式。
2. 本机运行随包测试：`node --test scripts/test-song-library.mjs`；再用 `node --check` 检查两份源文件。测试不登录、不联网、不调用真实 QQ 或 RVC。
3. 已有 `song-library` 时先检查是不是同一扩展。相同文件无需覆盖；不同先本机备份整个扩展，核对自定义行为再局部更新。冲突/不同作者同名时停止询问。复制 `index.mjs`、`library.mjs`、`request-guard.mjs`、`arrangement.mjs`、`acappella.mjs` 到 `<实际模块根>/song-library/`，不用覆盖核心 `src/song/studio.js`，也不替换已有库索引。入口最后替换，避免热加载读到缺依赖的半成品；有正在发送的清唱任务时先等待安全节点。
4. `libraryRoot` 从实际 `workspaceDir` 派生 `<workspaceDir>/大肥鱼歌曲库`。不存在才创建；索引不存在才初始化 `{"version":1,"items":[]}`。已有文件夹/索引先解析与盘点，坏索引先备份修复，不能写空清单“初始化”。自定义库位置需一起适配 `libraryRoot` 并测路径边界，不能移动用户旧库来强套模板。
5. 只为用户选择的已做成品补索引。探测时长、可解码和有声，计算 SHA256；保留原文件，复制使用不冲突文件名。索引项示例（这是格式，不是待写入的示例歌曲）：

```json
{"title":"用户指定的歌名","artist":"对应演唱者","version":"具体版本和片段说明","aliases":["用户确认的别名"],"file":"库内文件名.mp3","sha256":"实际文件哈希","createdAt":"实际时间"}
```

`file` 只能是库内普通 MP3 的文件名，不用绝对路径、`../` 或软链接。补充来源 `songId`、音色 `voice`、音调 `pitch`、时长与截取位置时必须来自实际制作记录。参数不符或记录缺失时入口保护先澄清，不自动重做。用户之前明确选过某个同名版本，可为该项写 `preferred:true`；否则不得擅自默认搜索第一版。当前匹配以更完整的名字/别名、明确演唱者/版本和用户已选默认版本为主，不能冒称完整参数缓存。没有用户确认不得擅自把不同歌或不同版本合并成别名。

6. 兼容的 1.1.11 可用 `POST /modules/reload`，body `{"id":"song-library"}`；首次发现如需要同步，先核对该版本行为。只操作本扩展，不重载内置 `song` 来清历史。若热载失败，停止并回滚扩展备份；需退出/重启时先检查现有任务并告知用户。
7. 用 `/modules` 核对本扩展已加载且无错误；`/ext/song-library/match?q=...` 返回的 `guard.mounted` 必须为真。按当前上游模拟接口测试明确命中的曲目，尤其是用户实际说过的原句，观察捕获的语音、队列无新增。**不要在真实宿主模拟未命中 `/sing` 来试回退**：模拟器虽拦截QQ发送，扩展的 `request` 仍可能真的排队。未命中/变调回退只用 mock 测试，直到用户明确请求制作。命中时 request 保留同步结果，`queued:false`，实际发送在后台完成；不能把“正在发送”冒称用户已收到。

## 自动入库与匹配限制

- 扩展在主人私聊发送链捕获 `[翻唱] ` 标记、base64 音频，按内容哈希去重并保留到库和索引；这是生产成品入库，不证明 QQ 已收到。发送失败也可能已经入库。发送前按 [清唱流程](acappella.md) 校验保留对应换声人声，后续可独立导出清唱；不靠最近文件名猜来源。
- 仅此发送链可自动收集；独立测试脚本生成、未经过该链的旧文件要由 Agent 补入。模板不自动解码探测收集的音频，也不保证从发送备注取得歌曲 ID/音色/时长，验收时补充核对。不随技能发测试歌曲。
- 同名多版本没有已确认默认值时需要澄清；模糊措辞、不同音色/音调请求需核对实际成品参数。已有同名成品但请求不同参数/重制时不自动开新任务，先确认版本和来源，再通过明确的制作路径处理。该模板不是完整自然语言意图引擎，只保护当前确认过的共享入口，新增外部制作入口仍需另测。
- 源文件可泛化复用；本机索引、别名、音频、账号信息不可拷到别人的部署。该包没有预置曲目。

## 分层验收和回滚

本机/mock：唯一命中、多版本澄清、不同版本不乱发、路径越界拒绝、缺文件明确失败、保存去重、非主人/群聊不越权、关闭/试运行不外发。真实宿主：加载无错、命中模拟不排队。获用户授权后再由主人私聊重复点同一已做曲目，两次都直接发成品，并核对实际播放；停止/重启后复验持久性。失败发送不能自动启动重制。

开发机当前 1.2.0 扩展通过28项隔离测试（含明确提供本机FFmpeg后的真实测试音导出），并已在运行宿主加载：入口保护 mounted=true；明确点歌、连续“上一首改成清唱/我要听清唱版的/换回带伴奏”的捕获式模拟命中正确成品，未新增制作队列，模拟记忆不影响真实上一首。原生新歌输出替换、保存人声及入库做了隔离测试，真实在途任务按完成证据另验收。**尚未在另一台机器安装/真实QQ收件验收**，不可称跨机一键保证成功。

回滚仅停用新增扩展或恢复本机备份，保留歌曲库和索引，不删成品，不改原插件缓存。下次升级先确认扩展仍加载、命令优先级不变，再复测；不能保证宿主升级永远兼容。
